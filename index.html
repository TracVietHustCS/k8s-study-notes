Kubernetes là gì?

Kubernetes (viết tắt K8s, vì có 8 chữ cái giữa “K” và “s”) là nền tảng mã nguồn mở để tự động hóa việc triển khai, mở rộng và vận hành ứng dụng đóng gói bằng container.

Dự án khởi nguồn từ Google, kế thừa kinh nghiệm chạy hệ thống nội bộ Borg. Kubernetes được công bố năm 2014, bản 1.0 ra năm 2015 và được trao cho CNCF (Cloud Native Computing Foundation) quản lý.

Kubernetes giải quyết vấn đề gì?

Chạy một container bằng docker run thì dễ. Chạy hàng trăm container trên nhiều máy, luôn sống, cập nhật không downtime thì cần một hệ điều phối.

Nhu cầuKubernetes làm gì
Điều phối (scheduling)Chọn node phù hợp để chạy Pod dựa trên CPU, RAM, ràng buộc.
Tự phục hồi (self-healing)Container chết thì khởi động lại, node chết thì tạo lại Pod ở node khác, không route traffic đến Pod chưa sẵn sàng.
Mở rộng (scaling)Tăng giảm số bản sao bằng tay hoặc tự động theo metric.
Cập nhật an toànRolling update và rollback khi có lỗi.
Service discovery và load balancingMỗi nhóm Pod có một địa chỉ và tên DNS ổn định.
Cấu hình và bí mậtTách config và secret khỏi image.
Lưu trữGắn volume từ nhiều loại storage khác nhau vào Pod.

Tư duy cốt lõi

  • Declarative: bạn mô tả trạng thái mong muốn (desired state) trong file YAML, không ra lệnh từng bước.
  • Reconciliation loop: các controller liên tục so sánh trạng thái thực tế (actual state) với desired state rồi hành động để hai bên khớp nhau.
  • API là trung tâm: mọi thứ là một object trong API server. kubectl, controller, kubelet đều chỉ là client của API.
  • Pod là tạm thời: Pod bị thay thế chứ không được “sửa tại chỗ”. Đừng phụ thuộc vào IP hay tên của một Pod cụ thể.
  • Liên kết lỏng bằng label: Service, Deployment tìm Pod qua label selector, không qua tên.
Ghi chú

Kubernetes không phải PaaS đầy đủ. Nó không build code, không có sẵn stack logging, monitoring hay CI/CD. Bạn ghép các công cụ đó vào xung quanh.

Kiến trúc cluster

Một cluster gồm control plane (ra quyết định) và các worker node (chạy ứng dụng).

Control plane và data plane

Control plane quản lý trạng thái cluster. Nó thường chạy trên các node riêng (master / control-plane node) và không chạy workload của người dùng. Data plane là các worker node, nơi Pod thực sự chạy.

Ghi nhớ

Mô hình hub-and-spoke: mọi thành phần chỉ nói chuyện với kube-apiserver. Scheduler không gọi kubelet trực tiếp mà ghi quyết định vào API, kubelet tự đọc về.

Tính sẵn sàng cao (HA)

  • Chạy nhiều control-plane node (thường 3). API server không giữ state nên đặt sau load balancer.
  • Scheduler và controller manager chạy nhiều bản nhưng chỉ một bản là leader tại một thời điểm (leader election).
  • etcd dùng thuật toán Raft, cần đa số (quorum = n/2 + 1) thành viên sống. Dùng số lẻ: 3 chịu được mất 1, 5 chịu được mất 2.
  • Topology: stacked (etcd chạy chung node control plane) hoặc external (cụm etcd riêng).

Các thành phần control plane

Năm thành phần ra quyết định và lưu trạng thái của cluster.

kube-apiserver

Cửa ngõ REST của cluster. Mọi client (kubectl, kubelet, controller) đều qua nó. Nó là thành phần duy nhất đọc ghi etcd.

Một request đi qua các bước:

  1. Authentication: bạn là ai (client cert, bearer token, OIDC, ServiceAccount token).
  2. Authorization: bạn có được làm việc này không (thường là RBAC).
  3. Admission control: mutating admission (có thể sửa object) rồi validating admission (chỉ chấp nhận hoặc từ chối).
  4. Validation và lưu vào etcd.

API server còn hỗ trợ cơ chế watch: client mở kết nối dài và nhận sự kiện khi object thay đổi. Đây là cách controller, scheduler, kubelet phản ứng gần như tức thời.

etcd

Key-value store phân tán, nhất quán mạnh, lưu toàn bộ trạng thái cluster (Pod, Secret, ConfigMap…). Mất etcd mà không có backup là mất cluster.

ETCDCTL_API=3 etcdctl snapshot save backup.db \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key
Cẩn thận

Secret trong etcd chỉ được mã hóa nếu bạn bật encryption at rest. Mặc định chúng chỉ là base64.

kube-scheduler

Theo dõi các Pod chưa có spec.nodeName và chọn node cho chúng, qua hai pha:

  1. Filtering: loại node không đủ điều kiện (thiếu tài nguyên, không khớp nodeSelector hoặc affinity, có taint không tolerate…).
  2. Scoring: chấm điểm các node còn lại (cân bằng tài nguyên, image đã có sẵn, spread…), chọn điểm cao nhất.

Cuối cùng scheduler tạo một binding ghi tên node vào Pod. Scheduler chỉ quyết định, kubelet mới là bên chạy Pod.

kube-controller-manager

Một tiến trình chạy nhiều controller. Mỗi controller là một vòng lặp:

for {
  desired := đọc spec từ API
  actual  := quan sát trạng thái thực tế
  if desired != actual { hành động để đưa actual về desired }
}
ControllerViệc chính
NodeTheo dõi node, đánh dấu NotReady, evict Pod khi node mất liên lạc quá lâu.
ReplicaSet / DeploymentGiữ đúng số Pod, điều khiển rolling update.
Job / CronJobTạo Pod chạy tới khi hoàn thành, chạy theo lịch.
EndpointSliceCập nhật danh sách IP Pod đứng sau Service.
ServiceAccount, NamespaceTạo ServiceAccount mặc định, dọn dẹp khi xóa namespace.

cloud-controller-manager

Chứa logic gắn với nhà cung cấp cloud: Node controller (xác nhận node còn tồn tại trên cloud), Route controller, Service controller (tạo cloud load balancer cho Service loại LoadBalancer). Cluster on-prem có thể không có thành phần này.

Thành phần trên Node và addons

Mỗi worker node cần ba thứ: kubelet, kube-proxy và container runtime.

kubelet

Agent chạy trên mỗi node, không chạy trong container mà thường là một dịch vụ systemd.

  • Đăng ký node với API server và báo cáo trạng thái, tài nguyên (heartbeat qua đối tượng Lease).
  • Theo dõi các Pod được gán cho node và gọi container runtime qua CRI để chạy chúng.
  • Chạy liveness, readiness, startup probe và báo kết quả.
  • Mount volume, tải Secret, ConfigMap vào Pod.
  • Chỉ quản lý container do Kubernetes tạo.

Static Pod: kubelet có thể chạy Pod từ file manifest trong một thư mục trên node (thường /etc/kubernetes/manifests) mà không cần API server. kubeadm dùng cách này để chạy apiserver, etcd, scheduler, controller-manager.

kube-proxy

Cài đặt các quy tắc mạng trên node để biến địa chỉ ảo của Service thành địa chỉ Pod thật và cân bằng tải. Các chế độ: iptables (phổ biến), ipvs, và nftables ở bản mới. Một số CNI như Cilium có thể thay thế hoàn toàn kube-proxy.

Container runtime

Phần mềm thực sự chạy container. Kubernetes giao tiếp với nó qua CRI (Container Runtime Interface).

  • containerd và CRI-O là hai runtime phổ biến, dùng chuẩn OCI.
  • Docker Engine không còn được hỗ trợ trực tiếp từ bản 1.24 khi dockershim bị gỡ. Image build bằng Docker vẫn chạy bình thường.
  • Công cụ debug trên node: crictl.

Chuyện gì xảy ra khi chạy kubectl apply?

Ví dụ kinh điển để hiểu cách các thành phần phối hợp. Giả sử bạn chạy kubectl apply -f deployment.yaml với replicas = 3.

  1. kubectl đọc file, đọc kubeconfig, gửi HTTPS request tới kube-apiserver.
  2. API server xác thực, phân quyền, chạy admission, validate rồi ghi object Deployment vào etcd.
  3. Deployment controller (watch API) thấy Deployment mới và tạo một ReplicaSet.
  4. ReplicaSet controller thấy cần 3 Pod mà đang có 0 nên tạo 3 object Pod (chưa có node).
  5. Scheduler thấy 3 Pod chưa có node, lọc và chấm điểm, ghi nodeName cho từng Pod.
  6. kubelet trên mỗi node được chọn thấy Pod gán cho mình và gọi container runtime qua CRI.
  7. Runtime kéo image, tạo sandbox (pause container), CNI cấp IP, rồi chạy container.
  8. kubelet chạy probe và cập nhật status của Pod về API server. Khi readiness thành công, Pod được thêm vào EndpointSlice của Service.
  9. kube-proxy trên các node cập nhật quy tắc để traffic của Service tới được Pod mới.
Mẹo nhớ

Không ai ra lệnh trực tiếp cho ai. Mỗi thành phần chỉ watch một loại object và làm phần việc của mình. Đó là lý do hệ thống tự hồi phục: xóa một Pod thì ReplicaSet controller lại thấy thiếu và tạo lại.

API objects, YAML, label và namespace

Mọi thứ trong Kubernetes là một object có cấu trúc giống nhau.

Cấu trúc một manifest

apiVersion: apps/v1        # nhóm API / phiên bản
kind: Deployment           # loại object
metadata:                  # định danh
  name: web
  namespace: demo
  labels: {app: web}
  annotations: {owner: "team-a"}
spec:                      # trạng thái mong muốn (bạn viết)
  replicas: 3
  # ...
status: {}                 # trạng thái thực tế (hệ thống ghi)
  • apiVersion: core group là v1 (Pod, Service, ConfigMap…), còn lại dạng nhóm/phiên bản như apps/v1, batch/v1, networking.k8s.io/v1, rbac.authorization.k8s.io/v1.
  • metadata: name (duy nhất trong namespace theo loại), uid, labels, annotations, ownerReferences, finalizers.
  • spec / status: bạn viết spec, controller cập nhật status.

Tên object phải theo chuẩn DNS-1123: chữ thường, số, - và ..

Namespace

Phân vùng logic trong một cluster, dùng để tách môi trường, team, và gắn quota hay RBAC.

Namespace mặc địnhMục đích
defaultNơi object được tạo khi không chỉ định.
kube-systemThành phần hệ thống (CoreDNS, kube-proxy…).
kube-publicDữ liệu đọc được công khai trong cluster.
kube-node-leaseLease heartbeat của node.

Không phải mọi object đều thuộc namespace. Các object cấp cluster gồm Node, PersistentVolume, StorageClass, ClusterRole, Namespace. Namespace không cô lập mạng. Muốn chặn traffic phải dùng NetworkPolicy.

Label, selector và annotation

  • Label: cặp key/value dùng để nhóm và chọn object (app=web, env=prod).
  • Selector: kiểu bằng (app=web) hoặc kiểu tập hợp (env in (prod,staging)).
  • Annotation: metadata không dùng để chọn, chứa thông tin tùy ý cho công cụ hoặc con người.
kubectl get pods -l app=web,env=prod
kubectl get pods -l 'env in (prod,staging)'
kubectl label pod web-1 tier=frontend

Imperative và declarative

# imperative: ra lệnh trực tiếp
kubectl create deployment web --image=nginx --replicas=3

# declarative: mô tả bằng file (nên dùng)
kubectl apply -f web.yaml

# sinh YAML mẫu mà không tạo gì
kubectl create deployment web --image=nginx --dry-run=client -o yaml > web.yaml

apply tạo hoặc cập nhật theo file, phù hợp với GitOps. create báo lỗi nếu đã tồn tại.

Mẹo

kubectl explain pod.spec.containers hiển thị tài liệu các field ngay trong terminal. Thêm --recursive để xem toàn cây.

Pod

Pod là đơn vị nhỏ nhất bạn triển khai. Một Pod gồm một hoặc nhiều container chạy cùng nhau trên cùng một node.

Các container trong Pod chia sẻ gì?

  • Network namespace: cùng một IP, giao tiếp với nhau qua localhost, không được trùng port.
  • Volume: có thể mount chung.
  • Có thể chia sẻ process namespace nếu bật.

Mỗi Pod có một container “pause” giữ network namespace để các container ứng dụng gắn vào.

Ví dụ đầy đủ

apiVersion: v1
kind: Pod
metadata:
  name: web
  labels:
    app: web
spec:
  containers:
    - name: nginx
      image: nginx:1.27
      ports:
        - containerPort: 80
      resources:
        requests: {cpu: 100m, memory: 128Mi}
        limits:   {memory: 256Mi}
      readinessProbe:
        httpGet: {path: /, port: 80}
        initialDelaySeconds: 3
        periodSeconds: 5
      livenessProbe:
        httpGet: {path: /, port: 80}
        periodSeconds: 10
  restartPolicy: Always

Vòng đời

PhaseÝ nghĩa
PendingĐã được chấp nhận nhưng chưa chạy: chờ schedule hoặc đang kéo image.
RunningĐã gán node, ít nhất một container đang chạy hoặc đang khởi động lại.
SucceededMọi container thoát với mã 0 và sẽ không khởi động lại (Job).
FailedMọi container đã dừng và có ít nhất một cái thất bại.
UnknownKhông lấy được trạng thái, thường do mất liên lạc với node.

Trạng thái của từng container: Waiting, Running, Terminated. restartPolicy gồm Always (mặc định), OnFailure, Never.

Init container và sidecar

  • Init container chạy tuần tự, xong hết mới tới container chính. Dùng để chờ dependency, tải config, chạy migration.
  • Sidecar chạy song song với container chính (log shipper, proxy). Bản K8s mới hỗ trợ sidecar chuẩn bằng init container có restartPolicy: Always, bảo đảm khởi động trước và tắt sau container chính.

Các pattern đa container: sidecar (mở rộng chức năng), ambassador (proxy ra ngoài), adapter (chuẩn hóa đầu ra).

Probes

ProbeHỏi gìKhi thất bại
startupProbeApp đã khởi động xong chưa?Kill và restart. Các probe khác tạm chờ.
livenessProbeApp còn sống không?kubelet restart container.
readinessProbeApp sẵn sàng nhận traffic chưa?Pod bị gỡ khỏi endpoints của Service, không restart.

Cơ chế kiểm tra: httpGet, tcpSocket, exec, grpc.

Cẩn thận

Liveness probe quá gắt hoặc phụ thuộc vào service ngoài có thể làm cả đàn Pod restart liên tục. Dùng startupProbe cho app khởi động chậm.

Requests, limits và QoS

  • requests: lượng tài nguyên scheduler dùng để chọn node và bảo đảm tối thiểu.
  • limits: trần sử dụng. Vượt CPU thì bị throttle, vượt memory thì bị OOMKilled.
  • CPU tính theo core (500m = 0,5 core), memory theo byte (Mi, Gi).
QoS classĐiều kiệnKhi node thiếu tài nguyên
GuaranteedMọi container có requests = limits (cả CPU và memory)Bị evict sau cùng
BurstableCó requests hoặc limits nhưng không thỏa GuaranteedỞ giữa
BestEffortKhông khai báo gìBị evict đầu tiên

Tắt Pod êm (graceful termination)

  1. Pod chuyển sang Terminating và bị gỡ khỏi endpoints.
  2. Chạy hook preStop (nếu có).
  3. Gửi SIGTERM cho tiến trình chính.
  4. Chờ tối đa terminationGracePeriodSeconds (mặc định 30 giây), hết hạn thì gửi SIGKILL.

Ứng dụng nên bắt SIGTERM để đóng kết nối và hoàn tất request đang xử lý.

ReplicaSet

Giữ đúng số bản sao Pod theo selector. Bạn hiếm khi dùng trực tiếp vì Deployment quản lý nó giúp bạn.

Deployment

apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3
  selector:
    matchLabels: {app: web}
  strategy:
    type: RollingUpdate
    rollingUpdate: {maxSurge: 25%, maxUnavailable: 25%}
  template:
    metadata:
      labels: {app: web}
    spec:
      containers:
        - name: nginx
          image: nginx:1.27
          ports: [{containerPort: 80}]
  • selector phải khớp label trong template và là bất biến sau khi tạo.
  • Mỗi lần sửa spec.template, Deployment tạo ReplicaSet mới và chuyển Pod dần từ cũ sang mới.
  • maxSurge: số Pod được vượt quá replicas khi update. maxUnavailable: số Pod được phép thiếu.
  • Chiến lược Recreate tắt hết Pod cũ rồi mới tạo Pod mới (có downtime).
kubectl set image deployment/web nginx=nginx:1.28
kubectl rollout status deployment/web
kubectl rollout history deployment/web
kubectl rollout undo deployment/web            # quay về bản trước
kubectl rollout undo deployment/web --to-revision=2
kubectl scale deployment/web --replicas=5
kubectl rollout restart deployment/web

StatefulSet

  • Pod có tên cố định theo thứ tự: db-0, db-1, db-2.
  • Tạo theo thứ tự 0, 1, 2 và xóa ngược lại (mặc định).
  • Cần một headless Service (clusterIP: None) để mỗi Pod có DNS riêng: db-0.db.ns.svc.cluster.local.
  • volumeClaimTemplates tạo một PVC riêng cho mỗi Pod. PVC được giữ lại khi Pod bị thay thế.

DaemonSet

Đảm bảo mỗi node (hoặc node khớp selector) chạy một Pod. Dùng cho log collector, monitoring agent, CNI, kube-proxy. Node mới vào cluster tự có Pod.

Job và CronJob

apiVersion: batch/v1
kind: CronJob
metadata:
  name: backup
spec:
  schedule: "0 2 * * *"            # 02:00 mỗi ngày
  concurrencyPolicy: Forbid
  successfulJobsHistoryLimit: 3
  jobTemplate:
    spec:
      backoffLimit: 3
      template:
        spec:
          restartPolicy: OnFailure
          containers:
            - name: backup
              image: busybox:1.36
              command: ["sh", "-c", "echo backup"]
  • Job: completions (số lần phải thành công), parallelism (số Pod chạy song song), backoffLimit (số lần thử lại).
  • Pod của Job phải có restartPolicy là OnFailure hoặc Never.
  • CronJob: concurrencyPolicy là Allow, Forbid hoặc Replace.

Service và DNS

Pod đến rồi đi, IP đổi liên tục. Service cho một nhóm Pod một địa chỉ và tên DNS ổn định kèm cân bằng tải.

Mô hình mạng của Kubernetes

  • Mỗi Pod có IP riêng.
  • Mọi Pod nói chuyện được với mọi Pod khác không qua NAT, dù ở node nào.
  • Node nói chuyện được với Pod trên chính nó.

Phần hiện thực do CNI plugin đảm nhiệm.

Manifest

apiVersion: v1
kind: Service
metadata:
  name: web
spec:
  type: ClusterIP
  selector:
    app: web            # chọn Pod theo label
  ports:
    - port: 80          # cổng của Service
      targetPort: 8080  # cổng container (số hoặc tên)

Controller tạo EndpointSlice chứa IP các Pod khớp selector và đang Ready. Pod không Ready sẽ không nhận traffic.

Các loại Service

TypeCách hoạt động
ClusterIP (mặc định)IP ảo chỉ truy cập được trong cluster.
NodePortMở thêm một cổng (30000–32767) trên mọi node, chuyển tới Service. Bao gồm ClusterIP.
LoadBalancerYêu cầu cloud tạo load balancer ngoài, trỏ vào NodePort. Bao gồm NodePort.
ExternalNameTrả về bản ghi CNAME tới một tên DNS ngoài, không proxy.
Headless (clusterIP: None)Không có IP ảo. DNS trả thẳng IP của các Pod. Dùng cho StatefulSet.

DNS

CoreDNS tạo bản ghi cho Service:

web                              # cùng namespace
web.demo                         # từ namespace khác
web.demo.svc.cluster.local       # tên đầy đủ (FQDN)

Pod của StatefulSet qua headless Service có tên dạng pod-0.svc.ns.svc.cluster.local.

Chi tiết cần nhớ

  • Tìm Service: qua DNS (khuyến nghị) hoặc biến môi trường WEB_SERVICE_HOST (chỉ có nếu Service tạo trước Pod).
  • sessionAffinity: ClientIP giữ một client dính vào cùng một Pod.
  • externalTrafficPolicy: Local giữ nguyên IP nguồn và bỏ một hop, nhưng chỉ gửi tới Pod trên node nhận traffic.
  • kube-proxy tạo quy tắc iptables hoặc IPVS để DNAT từ ClusterIP sang IP một Pod được chọn.

Ingress, Gateway API và NetworkPolicy

Đưa traffic HTTP(S) từ ngoài vào cluster và kiểm soát traffic giữa các Pod.

Ingress

Ingress là object khai báo luật định tuyến HTTP/HTTPS (host, path) tới các Service. Bản thân nó không làm gì. Bạn cần một Ingress controller (NGINX, Traefik, HAProxy…) đọc Ingress và thực thi.

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web
spec:
  ingressClassName: nginx
  tls:
    - hosts: [app.example.com]
      secretName: app-tls
  rules:
    - host: app.example.com
      http:
        paths:
          - path: /api
            pathType: Prefix
            backend:
              service: {name: api, port: {number: 80}}
          - path: /
            pathType: Prefix
            backend:
              service: {name: web, port: {number: 80}}
  • pathType: Exact, Prefix, ImplementationSpecific.
  • IngressClass chọn controller nào xử lý Ingress.
  • TLS lấy chứng chỉ từ Secret loại kubernetes.io/tls. Thường kết hợp cert-manager để cấp tự động.

Gateway API

Thế hệ tiếp theo của Ingress, biểu đạt tốt hơn và tách vai trò rõ ràng:

  • GatewayClass: loại hạ tầng (do nhà cung cấp quản lý).
  • Gateway: điểm vào, listener, cổng (do team hạ tầng quản lý).
  • HTTPRoute (và GRPCRoute, TCPRoute…): luật định tuyến (do team ứng dụng quản lý).
Ghi chú

Gateway API là hướng phát triển chính cho traffic vào cluster. Kiểm tra tình trạng hỗ trợ của controller bạn đang dùng trước khi chọn.

NetworkPolicy

Mặc định mọi Pod nói chuyện được với mọi Pod. NetworkPolicy là “tường lửa” L3/L4 cho Pod:

  • Chỉ có hiệu lực nếu CNI hỗ trợ (Calico, Cilium… có, Flannel thuần thì không).
  • Khi một Pod được chọn bởi ít nhất một policy theo chiều nào đó (Ingress hoặc Egress), mọi traffic chiều đó bị chặn trừ những gì được cho phép.
  • Các policy cộng dồn (union), không có luật deny.
# Chặn toàn bộ traffic vào namespace
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
spec:
  podSelector: {}
  policyTypes: [Ingress]
---
# Chỉ cho frontend gọi vào api cổng 8080
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-frontend
spec:
  podSelector:
    matchLabels: {app: api}
  policyTypes: [Ingress]
  ingress:
    - from:
        - podSelector:
            matchLabels: {app: frontend}
      ports:
        - port: 8080

ConfigMap và Secret

Tách cấu hình ra khỏi image để cùng một image chạy được ở nhiều môi trường.

ConfigMap

Lưu dữ liệu cấu hình không nhạy cảm dạng key/value (tối đa 1 MiB).

apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  LOG_LEVEL: info
  app.properties: |
    mode=prod
    retries=3

Ba cách dùng trong Pod:

containers:
  - name: app
    image: myapp:1.0
    env:
      - name: LOG_LEVEL
        valueFrom:
          configMapKeyRef: {name: app-config, key: LOG_LEVEL}
    envFrom:
      - configMapRef: {name: app-config}      # nạp mọi key thành env
    volumeMounts:
      - name: cfg
        mountPath: /etc/app
volumes:
  - name: cfg
    configMap: {name: app-config}              # mỗi key thành một file
  • Mount dạng volume sẽ tự cập nhật sau một khoảng trễ (tối đa vài chục giây). Mount bằng subPath thì không cập nhật.
  • Biến môi trường chỉ được nạp lúc container khởi động. Muốn đổi phải restart Pod.
  • Đặt immutable: true để chống sửa nhầm và giảm tải cho API server.

Secret

Giống ConfigMap nhưng dành cho dữ liệu nhạy cảm (mật khẩu, token, khóa TLS). Giá trị trong data được mã hóa base64.

TypeDùng cho

Cẩn thận

Base64 không phải mã hóa. Để an toàn hơn:

  • Bật encryption at rest cho etcd (hoặc dùng KMS provider).
  • Giới hạn RBAC đọc Secret chặt chẽ.
  • Ưu tiên mount dạng volume thay vì env để tránh lộ qua log hoặc dump môi trường.
  • Cân nhắc External Secrets Operator hoặc Secrets Store CSI Driver với Vault, AWS Secrets Manager…

Volume, PersistentVolume và PersistentVolumeClaim

Hệ thống file trong container mất khi container restart. Volume giúp dữ liệu sống lâu hơn container, và PV/PVC giúp dữ liệu sống lâu hơn Pod.

Các loại volume thường gặp

LoạiVòng đờiDùng cho
emptyDirTheo Pod (xóa khi Pod bị xóa)Thư mục tạm, chia sẻ file giữa các container
hostPathTheo nodeTruy cập file trên node (rủi ro bảo mật, hạn chế dùng)
configMap / secret / projectedTheo PodĐưa cấu hình vào dạng file
persistentVolumeClaimĐộc lập với PodDữ liệu bền vững

PV, PVC và StorageClass

  • PersistentVolume (PV): một phần storage trong cluster (cấp cluster, không thuộc namespace).
  • PersistentVolumeClaim (PVC): yêu cầu storage của người dùng (thuộc namespace): dung lượng, access mode, class.
  • StorageClass: mô tả “loại” storage và cách cấp phát động (provisioner, tham số).
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: data
spec:
  accessModes: [ReadWriteOnce]
  storageClassName: standard
  resources:
    requests:
      storage: 10Gi
---
# dùng trong Pod
spec:
  containers:
    - name: app
      image: myapp:1.0
      volumeMounts:
        - {name: data, mountPath: /var/lib/app}
  volumes:
    - name: data
      persistentVolumeClaim: {claimName: data}

Luồng cấp phát

  1. User tạo PVC.
  2. Dynamic provisioning: StorageClass tạo PV mới qua CSI driver. (Static: admin tạo sẵn PV, PVC tìm PV khớp.)
  3. PVC được bound với PV (quan hệ 1-1).
  4. Pod mount PVC. Khi xóa PVC, số phận dữ liệu tùy reclaimPolicy.

Access modes

ModeÝ nghĩa
ReadWriteOnce (RWO)Đọc ghi bởi một node
ReadOnlyMany (ROX)Đọc bởi nhiều node
ReadWriteMany (RWX)Đọc ghi bởi nhiều node (NFS, CephFS, EFS…)
ReadWriteOncePod (RWOP)Đọc ghi bởi đúng một Pod

Reclaim policy và các tùy chọn

  • Delete: xóa PV và storage thật khi PVC bị xóa (mặc định cho dynamic).
  • Retain: giữ lại dữ liệu, admin xử lý thủ công.
  • allowVolumeExpansion: true trên StorageClass cho phép tăng dung lượng PVC.
  • volumeBindingMode: WaitForFirstConsumer trì hoãn tạo volume tới khi Pod được schedule, tránh volume nằm khác zone với Pod.
  • CSI (Container Storage Interface) là chuẩn để hãng storage viết driver. VolumeSnapshot hỗ trợ chụp snapshot.

Điều khiển việc xếp Pod lên Node

Scheduler có logic mặc định tốt. Bạn can thiệp khi cần chỉ định hoặc tránh node cụ thể.

nodeSelector và node affinity

spec:
  nodeSelector:
    disktype: ssd
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
          - matchExpressions:
              - {key: topology.kubernetes.io/zone, operator: In, values: [a, b]}
      preferredDuringSchedulingIgnoredDuringExecution:
        - weight: 50
          preference:
            matchExpressions:
              - {key: disktype, operator: In, values: [ssd]}
  • required…: bắt buộc (hard). preferred…: ưu tiên (soft).
  • IgnoredDuringExecution: nếu label node đổi sau khi Pod đã chạy, Pod không bị đuổi.

Pod affinity và anti-affinity

Quyết định dựa trên các Pod khác đang chạy ở đó. topologyKey xác định “miền” (kubernetes.io/hostname là node, topology.kubernetes.io/zone là zone).

affinity:
  podAntiAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector:
          matchLabels: {app: web}
        topologyKey: kubernetes.io/hostname      # mỗi node tối đa một Pod web

Taints và tolerations

Taint gắn lên node để đẩy Pod ra. Toleration gắn lên Pod để cho phép chịu taint đó.

EffectÝ nghĩa
NoScheduleKhông xếp Pod mới lên node (trừ Pod có toleration)
PreferNoScheduleCố gắng tránh, không bắt buộc
NoExecuteKhông xếp mới và đuổi các Pod đang chạy không có toleration
kubectl taint nodes node1 dedicated=gpu:NoSchedule
kubectl taint nodes node1 dedicated=gpu:NoSchedule-     # gỡ taint

tolerations:
  - key: dedicated
    operator: Equal
    value: gpu
    effect: NoSchedule
Ghi nhớ

Taint/toleration chỉ cho phép Pod lên node. Để bắt Pod lên đúng node đó, kết hợp thêm nodeSelector hoặc node affinity.

Topology spread constraints

topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: topology.kubernetes.io/zone
    whenUnsatisfiable: DoNotSchedule
    labelSelector:
      matchLabels: {app: web}

Rải đều Pod giữa các zone hoặc node. maxSkew là độ lệch tối đa cho phép.

Ưu tiên và bảo trì node

  • PriorityClass: Pod ưu tiên cao có thể preempt (đuổi) Pod ưu tiên thấp khi cluster hết chỗ.
  • cordon đánh dấu node không nhận Pod mới. drain cordon rồi di tản Pod. uncordon mở lại.
  • PodDisruptionBudget (PDB): giới hạn số Pod được phép down cùng lúc khi bị di tản chủ động.
  • ResourceQuota giới hạn tổng tài nguyên của namespace. LimitRange đặt mặc định và biên min/max cho từng Pod/container.
kubectl cordon node1
kubectl drain node1 --ignore-daemonsets --delete-emptydir-data
kubectl uncordon node1

Autoscaling

Ba tầng tự co giãn: số Pod, kích thước Pod và số Node.

Horizontal Pod Autoscaler (HPA)

Tăng giảm số replica của Deployment/StatefulSet theo metric (CPU, memory, metric tùy chỉnh). Cần metrics-server và Pod phải khai báo requests (HPA tính % theo request).

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: web
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: web
  minReplicas: 2
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target: {type: Utilization, averageUtilization: 70}

Công thức: desiredReplicas = ceil[ currentReplicas × currentMetric / targetMetric ]. Ví dụ 4 replicas đang dùng 90% CPU, mục tiêu 60% thì cần ceil(4 × 90 / 60) = 6.

kubectl autoscale deployment web --min=2 --max=10 --cpu-percent=70
kubectl get hpa -w

Vertical Pod Autoscaler (VPA)

Đề xuất hoặc tự điều chỉnh requests/limits của Pod theo mức dùng thực tế. Là add-on riêng. Thay đổi resource thường cần restart Pod. Không nên để VPA và HPA cùng điều khiển một metric CPU/memory.

Cluster Autoscaler / Karpenter

  • Thêm node khi có Pod Pending do thiếu tài nguyên.
  • Bớt node khi node dư và Pod trên đó di chuyển được.
  • Thường tích hợp với node group của cloud.
Mẹo

KEDA mở rộng HPA để scale theo sự kiện (độ dài queue, lag Kafka…) và có thể scale về 0.

RBAC và bảo mật

Bảo mật nhiều lớp: ai được vào, được làm gì, Pod được phép chạy thế nào, và traffic nào được đi.

Xác thực và phân quyền

  • Authentication: client certificate, bearer token, OIDC, ServiceAccount token. Kubernetes không có object “User”, danh tính đến từ nguồn bên ngoài.
  • Authorization: RBAC là chuẩn. Chỉ có luật cho phép (allow), không có deny.

RBAC

ObjectPhạm viVai trò
RoleMột namespaceTập quyền (verbs trên resources)

RoleBindingMột namespaceGán Role/ClusterRole cho subject trong namespace đó
ClusterRoleBindingToàn clusterGán ClusterRole cho subject trên toàn cluster

kind: Role
metadata:
  namespace: dev
  name: pod-reader
rules:
  - apiGroups: [""]
    resources: ["pods", "pods/log"]
    verbs: ["get", "list", "watch"]
---

kind: RoleBinding
metadata:
  namespace: dev
  name: read-pods

  - kind: ServiceAccount
    name: app-sa

  kind: Role
  name: pod-reader

kubectl auth can-i list secrets --as=system:serviceaccount:dev:app-sa -n dev
Cẩn thận

Tránh gán cluster-admin bừa bãi. Áp dụng nguyên tắc least privilege: quyền tối thiểu cần thiết, ưu tiên Role theo namespace.

ServiceAccount

Danh tính cho tiến trình trong Pod khi gọi API server. Mỗi namespace có ServiceAccount default. Token được cấp dạng ngắn hạn, gắn với Pod (bound token). Nếu app không cần gọi API, đặt automountServiceAccountToken: false.

Admission và Pod Security

  • Admission controller: chặn hoặc sửa request sau khi xác thực/phân quyền. Mở rộng bằng webhook, ValidatingAdmissionPolicy, hoặc công cụ như OPA Gatekeeper, Kyverno.
  • Pod Security Admission thay thế PodSecurityPolicy (đã gỡ ở 1.25). Ba mức: privileged, baseline, restricted. Ba chế độ: enforce, audit, warn.
kubectl label ns dev pod-security.kubernetes.io/enforce=restricted

securityContext

spec:
  securityContext:
    runAsNonRoot: true
    runAsUser: 10001
    seccompProfile: {type: RuntimeDefault}
  containers:
    - name: app
      image: myapp:1.0
      securityContext:
        allowPrivilegeEscalation: false
        readOnlyRootFilesystem: true
        capabilities: {drop: ["ALL"]}

Checklist nhanh

  • Chạy container không phải root, bỏ capability thừa, root filesystem chỉ đọc.
  • Dùng NetworkPolicy theo hướng mặc định chặn.
  • Quét image, dùng tag cố định hoặc digest, registry tin cậy.
  • Mã hóa Secret at rest, bật audit logging, cập nhật Kubernetes thường xuyên.
  • Không để API server lộ ra Internet công khai.

Service không truy cập được

  1. Pod có chạy và Ready không? kubectl get pods -l app=web
  2. Selector của Service có khớp label Pod không? kubectl get endpointslices. Rỗng nghĩa là không khớp hoặc không Ready.
  3. targetPort có đúng cổng container đang lắng nghe không?
  4. Gọi thử từ trong cluster: kubectl run tmp --rm -it --image=busybox:1.36 -- wget -qO- web
  5. DNS ổn không? nslookup web. Kiểm tra CoreDNS ở kube-system.
  6. Có NetworkPolicy nào chặn không?
  7. Với Ingress: controller có chạy không, ingressClassName đúng chưa, host và path khớp chưa?

Pod Security Admission, ValidatingAdmissionPolicy và policy engine

Ba lớp để kiểm soát “Pod nào được phép chạy”: PSA có sẵn trong Kubernetes, ValidatingAdmissionPolicy viết luật bằng CEL, và các policy engine như Kyverno, Gatekeeper cho nhu cầu phức tạp hơn.

Bối cảnh

  • PodSecurityPolicy (PSP) đã bị gỡ ở 1.25.
  • Pod Security Standards (PSS) là bộ tiêu chuẩn gồm ba profile. Pod Security Admission (PSA) là admission controller built-in để áp dụng PSS lên namespace.
  • PSA đơn giản, không cần cài thêm gì, nhưng cứng: chỉ ba mức, áp theo namespace, không sửa (mutate) được Pod.

Ba profile của PSS

ProfileÝ nghĩaChặn những gì (tiêu biểu)
privilegedKhông hạn chếKhông chặn gì. Dành cho hệ thống như CNI, CSI, agent giám sát.
baselineChặn các leo thang đặc quyền đã biết, ít ảnh hưởng ứng dụngprivileged: true, hostNetwork/hostPID/hostIPC, hostPath volume, hostPort, thêm capability nguy hiểm, seccomp Unconfined, sysctl không an toàn.
restrictedTheo best practice hardening hiện hànhMọi thứ của baseline, cộng thêm: bắt buộc runAsNonRoot: true, allowPrivilegeEscalation: false, drop ALL capabilities (chỉ được thêm lại NET_BIND_SERVICE), seccomp RuntimeDefault hoặc Localhost, chỉ cho các loại volume an toàn.

Ba chế độ (mode)

ModeKhi vi phạm
enforceTừ chối tạo Pod.
auditCho phép, nhưng ghi annotation vào audit log.
warnCho phép, nhưng trả cảnh báo cho người chạy kubectl.

Cấu hình bằng label trên namespace, mỗi mode độc lập nhau. Có thể ghim phiên bản của chính sách bằng -version để nâng cấp cluster không làm đổi luật đột ngột.

kubectl label ns payments \
  pod-security.kubernetes.io/enforce=baseline \
  pod-security.kubernetes.io/enforce-version=latest \
  pod-security.kubernetes.io/warn=restricted \
  pod-security.kubernetes.io/audit=restricted

Rollout an toàn vào cluster đang chạy

  1. Đặt warn và audit ở mức mong muốn (thường restricted), chưa bật enforce.
  2. Chạy thử với server-side dry-run để xem namespace nào sẽ bị ảnh hưởng: 
    kubectl label --dry-run=server --overwrite ns --all \
  pod-security.kubernetes.io/enforce=baseline
  3. Sửa workload vi phạm (thêm securityContext), theo dõi cảnh báo.
  4. Bật enforce từng namespace, trước tiên là các namespace ứng dụng.
Cẩn thận

Namespace chạy CNI, CSI, node-exporter hay log agent thường cần privileged. Đừng bật restricted hàng loạt cho kube-system. Nếu cần ngoại lệ, dùng AdmissionConfiguration để exempt theo username, namespace hoặc runtimeClass.

Pod đạt chuẩn restricted

apiVersion: v1
kind: Pod
metadata:
  name: safe
spec:
  securityContext:
    runAsNonRoot: true
    seccompProfile: {type: RuntimeDefault}
  containers:
    - name: app
      image: myapp:1.0
      securityContext:
        allowPrivilegeEscalation: false
        capabilities: {drop: ["ALL"]}
        readOnlyRootFilesystem: true

ValidatingAdmissionPolicy (VAP)

Luật validate viết bằng biểu thức CEL, chạy ngay trong API server, không cần webhook ngoài (nhanh hơn, ít điểm lỗi hơn). Ổn định (GA) từ 1.30. Gồm hai object: policy và binding.

apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicy
metadata:
  name: max-replicas
spec:
  failurePolicy: Fail
  matchConstraints:
    resourceRules:
      - apiGroups: ["apps"]
        apiVersions: ["v1"]
        operations: ["CREATE", "UPDATE"]
        resources: ["deployments"]
  validations:
    - expression: "object.spec.replicas <= 5"
      message: "replicas phải <= 5"
---
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicyBinding
metadata:
  name: max-replicas-binding
spec:
  policyName: max-replicas
  validationActions: [Deny]        # hoặc Warn, Audit
  matchResources:
    namespaceSelector:
      matchLabels: {env: prod}

Bản K8s mới còn bổ sung policy dạng mutate. Kiểm tra trạng thái tính năng theo phiên bản bạn dùng.

Ghi chú

Cú pháp của Kyverno thay đổi giữa các phiên bản (ví dụ vị trí của failureAction). Kiểm tra tài liệu đúng phiên bản bạn cài.

Chọn công cụ nào?

  • Chỉ cần chặn pod đặc quyền: PSA là đủ.
  • Luật validate đơn giản theo từng object: VAP.
  • Cần mutate, generate, verify image, báo cáo tuân thủ: Kyverno hoặc Gatekeeper.
  • Các lớp này kết hợp được: PSA làm nền, policy engine bổ sung luật riêng của tổ chức.

Chuỗi cung ứng và runtime

  • Quét image (Trivy, Grype), ký image (cosign) và kiểm chữ ký lúc admission, dùng digest thay vì tag.
  • Runtime: seccomp, AppArmor, SELinux. Giám sát hành vi bằng Falco hoặc Tetragon.
  • Cô lập mạnh hơn: RuntimeClass với gVisor hoặc Kata Containers.

Helm và Kustomize

Quản lý hàng chục manifest YAML bằng tay rất dễ lỗi. Helm đóng gói chúng thành chart có tham số và có vòng đời cài đặt, còn Kustomize vá YAML thuần theo từng môi trường.

Helm là gì?

  • Chart: gói chứa template K8s và giá trị mặc định.
  • Release: một lần cài chart vào cluster với tên riêng. Cùng một chart cài được nhiều release.
  • Repository / OCI registry: nơi lưu chart (HTTP repo hoặc OCI như ECR, GHCR, Harbor).
  • Values: tham số để tùy biến, ghi đè bằng -f values.yaml hoặc --set.
Ghi chú

Helm 3 không còn Tiller. Helm chạy phía client bằng quyền kubeconfig của bạn, lưu trạng thái release dưới dạng Secret (helm.sh/release.v1) trong namespace của release.

Cấu trúc chart

mychart/
  Chart.yaml          # tên, version chart, appVersion, dependencies
  values.yaml         # giá trị mặc định
  templates/
    deployment.yaml
    service.yaml
    _helpers.tpl      # hàm dùng chung
    NOTES.txt         # hướng dẫn in sau khi cài
  charts/             # chart phụ thuộc
  values.schema.json  # (tùy chọn) kiểm tra values
# templates/deployment.yaml (rút gọn)
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ include "mychart.fullname" . }}
spec:
  replicas: {{ .Values.replicaCount }}
  template:
    spec:
      containers:
        - name: app
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag | default .Chart.AppVersion }}"
          {{- with .Values.resources }}
          resources: {{- toYaml . | nindent 12 }}
          {{- end }}

Template dùng Go template cộng thư viện Sprig: .Values, .Release.Name, .Chart, include, toYaml, nindent, default, required.

Điều cần nhớ

  • Hooks: annotation helm.sh/hook (pre-install, post-upgrade, pre-delete…) chạy Job vào các thời điểm của release, ví dụ migrate database.
  • Upgrade không cập nhật CRD trong thư mục crds/. CRD chỉ được cài lần đầu. Cần quy trình riêng để nâng cấp CRD.
  • Rollback quay về revision cũ của release, nhưng không hoàn tác dữ liệu, PVC hay thay đổi ngoài chart.
  • Plugin helm-diff cho xem trước thay đổi trước khi upgrade.
  • Secret trong values: dùng SOPS (helm-secrets) hoặc External Secrets, không commit plaintext.
  • Kiểm tra nguồn chart: chart bên thứ ba có thể cài bất kỳ thứ gì. Xem helm template trước khi cài vào production.

GitOps với Argo CD và Flux

Git là nguồn sự thật duy nhất của cluster. Một operator chạy trong cluster liên tục kéo cấu hình từ Git về và đưa cluster khớp với nó.

Nguyên tắc GitOps

  • Declarative: trạng thái mong muốn được mô tả bằng manifest, Helm hoặc Kustomize.
  • Versioned: lưu trong Git, có review, lịch sử và revert.
  • Pulled: agent trong cluster kéo về (pull), CI không cần quyền truy cập cluster (khác với CI đẩy bằng kubectl apply).
  • Continuously reconciled: phát hiện và sửa drift. Ai sửa tay trên cluster sẽ bị ghi đè (nếu bật self-heal).
Mẹo

Tách repo: repo ứng dụng (code, CI build image) và repo cấu hình (manifest triển khai). CI build xong chỉ cập nhật tag image trong repo cấu hình, GitOps lo phần còn lại.

Argo CD

Có giao diện web trực quan, hiển thị cây tài nguyên, health và diff. Object chính:

  • Application: ánh xạ một nguồn (Git path, Helm chart) tới một đích (cluster, namespace).
  • AppProject: nhóm Application, giới hạn repo, cluster, namespace và loại resource được phép.
  • ApplicationSet: sinh nhiều Application từ template (theo danh sách cluster, thư mục Git, PR…).
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: web
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/ORG/REPO.git
    targetRevision: main
    path: apps/web
  destination:
    server: https://kubernetes.default.svc
    namespace: demo
  syncPolicy:
    automated:
      prune: true        # xóa resource không còn trong Git
      selfHeal: true     # sửa lại khi có drift
    syncOptions:
      - CreateNamespace=true
  • Sync status: Synced hoặc OutOfSync. Health: Healthy, Progressing, Degraded, Missing.
  • Sync waves và hooks: điều khiển thứ tự (annotation argocd.argoproj.io/sync-wave, hook PreSync/PostSync).
  • App of Apps hoặc ApplicationSet để bootstrap cả cluster từ một Application gốc.
  • Quản lý được nhiều cluster từ một Argo CD (hub-and-spoke).
  • Bộ đôi Argo Rollouts bổ sung canary và blue-green.

CNI: AWS VPC CNI, Calico, Cilium và Hubble

CNI quyết định Pod lấy IP từ đâu, đi qua mạng thế nào, và NetworkPolicy được thực thi ra sao. Chọn CNI ảnh hưởng hiệu năng, quan sát và giới hạn của cluster.

CNI hoạt động thế nào

  • CNI (Container Network Interface) là chuẩn gồm plugin (file thực thi trong /opt/cni/bin) và cấu hình trong /etc/cni/net.d.
  • Khi tạo sandbox cho Pod, container runtime gọi plugin với lệnh ADD (cấp IP, tạo veth, cấu hình route). Khi xóa Pod gọi DEL.
  • Thường chạy dạng DaemonSet kèm một agent trên mỗi node.
  • Chưa cài CNI thì node NotReady và Pod kẹt ở ContainerCreating.

AWS VPC CNI

CNI mặc định của EKS. Pod nhận địa chỉ IP thật của VPC (secondary IP gắn trên ENI của node), nên không có overlay.

  • Thành phần: DaemonSet aws-node chạy ipamd giữ pool IP sẵn sàng cho node.
  • Ưu điểm: hiệu năng như mạng VPC, Security Group, VPC Flow Logs và routing của AWS dùng được trực tiếp với Pod, dịch vụ ngoài thấy IP Pod thật.
  • Nhược điểm: mỗi Pod tốn một IP của subnet nên dễ cạn IP. Số Pod trên mỗi node bị giới hạn bởi loại instance.

Công thức giới hạn: maxPods = số ENI × (số IPv4 mỗi ENI − 1) + 2. Ví dụ m5.large có 3 ENI, mỗi ENI 10 IP, nên tối đa 3 × 9 + 2 = 29 Pod.

Calico

  • Mạnh về routing và policy. Có thể chạy BGP không overlay, hoặc IP-in-IP, VXLAN, hoặc mã hóa bằng WireGuard.
  • Dataplane: iptables (phổ biến), nftables, hoặc eBPF.
  • Thành phần: calico-node (chạy Felix lo policy và route, BIRD lo BGP), Typha (giảm tải datastore khi cluster lớn), calico-kube-controllers. Cài bằng Tigera operator.

  • Có thể dùng chỉ để làm policy trên EKS, chạy cạnh VPC CNI (VPC CNI lo IP, Calico lo policy).

Cilium và Hubble

  • Xây trên eBPF. Có thể thay hoàn toàn kube-proxy (kubeProxyReplacement), cân bằng tải hiệu quả không qua iptables.

Lớp observability của Cilium: xem luồng mạng giữa các Pod theo thời gian thực, có verdict (FORWARDED, DROPPED) và cả thông tin L7. Rất hữu ích để debug NetworkPolicy.

CSI: kiến trúc, AWS EBS và NetApp Trident

CSI (Container Storage Interface) là chuẩn để hãng storage viết driver chạy ngoài lõi Kubernetes. Mọi storage hiện đại (EBS, Ceph, NetApp, Azure Disk…) đều đi qua CSI.

Kiến trúc driver

Một driver gồm hai phần, giao tiếp qua gRPC với ba dịch vụ Identity, Controller, Node:

Thành phầnChạy dưới dạngViệc chính
Controller pluginDeployment (thường 2 bản)Tạo, xóa, attach, resize, snapshot volume trên hệ thống storage. Đi kèm các sidecar: external-provisioner, external-attacher, external-resizer, external-snapshotter.
Node pluginDaemonSetTrên mỗi node: format, mount volume và bind-mount vào Pod. Đi kèm node-driver-registrar để đăng ký với kubelet.

Luồng cấp phát một volume

  1. PVC được tạo. external-provisioner gọi CreateVolume tạo volume trên storage, rồi tạo PV tương ứng.
  2. Pod được schedule. external-attacher gọi ControllerPublishVolume (attach volume vào node, tạo object VolumeAttachment).
  3. kubelet gọi NodeStageVolume: format và mount volume vào thư mục staging chung của node.
  4. kubelet gọi NodePublishVolume: bind-mount vào đường dẫn riêng của Pod.

Object liên quan: CSIDriver, CSINode, VolumeAttachment, StorageClass, VolumeSnapshotClass, VolumeSnapshot, VolumeSnapshotContent.

AWS EBS CSI driver

Driver ebs.csi.aws.com cấp EBS volume (block storage) cho Pod. Trên EKS cài như một add-on (aws-ebs-csi-driver).

  • Volume EBS gắn với một AZ và gần như chỉ RWO (một node tại một thời điểm). Pod phải chạy cùng AZ với volume.
  • Vì vậy StorageClass nên dùng volumeBindingMode: WaitForFirstConsumer để volume được tạo ở đúng AZ của Pod.
  • Driver cần quyền IAM (tạo, attach, xóa volume): dùng IRSA hoặc EKS Pod Identity cho ServiceAccount của controller.
  • Hỗ trợ expand online, snapshot (qua EBS snapshot), mã hóa bằng KMS.
  • Cần RWX: dùng EFS CSI (efs.csi.aws.com) hoặc FSx.
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata: {name: ebs-gp3}
provisioner: ebs.csi.aws.com
parameters:
  type: gp3
  encrypted: "true"
  # iops: "6000"          # tùy chọn cho gp3
  # throughput: "250"
volumeBindingMode: WaitForFirstConsumer
allowVolumeExpansion: true
reclaimPolicy: Delete
Cẩn thận

Lỗi hay gặp: Multi-Attach error khi Pod được schedule sang node khác trong lúc volume còn gắn ở node cũ, hoặc Pod Pending vì volume nằm ở AZ không có node trống. Kiểm tra kubectl get volumeattachment và log của ebs-csi-controller.

NetApp Trident

Trident là CSI provisioner mã nguồn mở của NetApp (csi.trident.netapp.io), cấp volume từ các hệ thống NetApp: ONTAP on-prem, Cloud Volumes ONTAP, Amazon FSx for NetApp ONTAP, Azure NetApp Files…

  • Cài bằng Trident operator hoặc Helm, thường vào namespace trident.
  • Backend mô tả kết nối tới storage, tạo bằng CRD TridentBackendConfig (TBC) hoặc tridentctl create backend.
  • Driver ONTAP phổ biến: ontap-nas (NFS, mỗi PVC một FlexVol), ontap-nas-economy (nhiều PVC chung một FlexVol), ontap-nas-flexgroup, ontap-san (iSCSI hoặc NVMe), ontap-san-economy.
  • NAS (NFS) cho RWX dễ dàng, SAN (block) cho workload cần hiệu năng như database.
  • Có snapshot, clone nhanh từ PVC hoặc snapshot (tận dụng FlexClone), import volume có sẵn, expand.

kubeadm: xe số sàn

kubeadm là công cụ chính thức để dựng cluster đúng chuẩn upstream. Nó chỉ lo phần bootstrap, không cài CNI, không có load balancer, không có storage.

kubeadm init --control-plane-endpoint "k8s-api.example.com:6443" --upload-certs
kubeadm join ... --control-plane --certificate-key ...   # thêm control plane
kubeadm join ...                                          # thêm worker
kubeadm certs check-expiration
kubeadm upgrade plan && kubeadm upgrade apply v1.xx.y
  • Học được rất nhiều: bạn thấy cert, static pod, etcd, kubelet config. Hợp để luyện thi CKA.
  • Đau khi lên production: HA phải tự dựng (HAProxy, kube-vip), certificate hết hạn sau khoảng 1 năm nếu quên gia hạn, upgrade từng minor một, lần lượt control plane rồi worker, và tự backup etcd.
  • Nhiều distro và Cluster API dựng trên kubeadm bên dưới.

k3s: nhẹ, nhanh, tiện

Distro Kubernetes đã được CNCF chứng nhận conformant, do Rancher (nay thuộc SUSE) phát triển. Đóng gói thành một binary nhỏ, bỏ bớt các thành phần cũ và alpha.

curl -sfL https://get.k3s.io | sh -                       # server
sudo cat /var/lib/rancher/k3s/server/node-token            # lấy token
curl -sfL https://get.k3s.io | K3S_URL=https://SERVER:6443 K3S_TOKEN=... sh -   # agent
# HA với etcd nhúng
curl -sfL https://get.k3s.io | sh -s - server --cluster-init
  • Datastore: mặc định SQLite (một server), hoặc etcd nhúng cho HA, hoặc DB ngoài (PostgreSQL, MySQL) qua kine.
  • Kèm sẵn: containerd, Flannel, CoreDNS, Traefik, ServiceLB (klipper-lb), local-path-provisioner, metrics-server.
  • Chém: cài vài chục giây, chạy ngon trên Raspberry Pi và VM nhỏ, rất hợp edge, lab và cluster tạm cho CI (k3d chạy k3s trong Docker). Đổi lại các mặc định “tiện” (Traefik, ServiceLB, SQLite) thường phải thay hoặc tắt khi lên production, và ServiceLB không phải load balancer thật.

RKE2: ông anh khó tính của k3s

Distro của SUSE Rancher nhắm vào môi trường cần bảo mật và tuân thủ (chính phủ, tài chính).

  • Hardening theo CIS Benchmark, hỗ trợ chế độ FIPS 140, SELinux.
  • Control plane chạy dạng static pod, runtime là containerd, CNI mặc định thường là Canal (Calico + Flannel), có thể chọn Cilium.
  • Cài tương tự k3s nhưng nặng hơn, đổi lại ít phải tự hardening.
curl -sfL https://get.rke2.io | sh -
systemctl enable --now rke2-server.service

Rancher (SUSE): trạm điều khiển đa cluster

Rancher không phải một distro Kubernetes. Nó là management plane: một ứng dụng chạy trên một cluster (thường RKE2 hoặc k3s, cài bằng Helm) để quản lý nhiều cluster khác.

  • Tạo cluster (RKE2, k3s trên VM) hoặc import cluster có sẵn, quản lý luôn EKS, AKS, GKE.
  • Đăng nhập tập trung (AD, LDAP, OIDC, SAML), RBAC theo cluster và Project, chính sách chung.
  • Fleet cho GitOps ở quy mô nhiều cluster. Ngoài ra có các chart giám sát, logging, Longhorn (storage), NeuVector (bảo mật), Harvester (HCI trên bare metal, chạy VM bằng KubeVirt).
  • Chém: giao diện tốt, rất đáng dùng khi có nhiều cluster và nhiều team. Nhưng đừng coi nó là phép màu: bản thân Rancher server cần HA, backup và upgrade đúng ma trận tương thích. Gói thương mại có tên Rancher Prime.

EKS: AWS lo control plane

AWS vận hành API server và etcd trải trên nhiều AZ. Bạn lo phần data plane và mọi thứ bên trên.

  • Compute: managed node group, self-managed node, Fargate, Karpenter (autoscale node), hoặc EKS Auto Mode (AWS quản lý cả node và nhiều add-on).
  • Mạng: VPC CNI mặc định, AWS Load Balancer Controller (ALB cho Ingress, NLB cho Service).
  • Danh tính: IAM vào cluster qua access entries (cách mới, thay aws-auth ConfigMap), Pod gọi AWS API qua IRSA hoặc EKS Pod Identity.
  • Add-ons: vpc-cni, coredns, kube-proxy, EBS/EFS CSI quản lý qua EKS add-on.
  • Upgrade: mỗi lần một minor, lần lượt control plane, add-on, rồi node. Mỗi phiên bản có thời gian hỗ trợ chuẩn và có thể gia hạn có phí (extended support), nên đừng để cluster quá cũ.
eksctl create cluster --name demo --region ap-southeast-1 --nodes 3
aws eks update-kubeconfig --name demo --region ap-southeast-1
kubectl get nodes

Chém: bớt hẳn nỗi đau etcd và control plane, tích hợp sâu với IAM, ALB, EBS. Cái giá: tiền lẻ tẻ (phí cluster theo giờ cộng EC2, NAT gateway, load balancer, data transfer), cạn IP với VPC CNI, và upgrade vẫn là việc của bạn. Dùng Terraform hoặc eksctl chứ đừng click console.

Nutanix: NKP và NKE

  • NKE (Nutanix Kubernetes Engine, tiền thân là Karbon): tích hợp trong Prism Central, tạo cluster K8s trên AHV bằng vài cú click, hợp đội IT đã quen Nutanix.
  • NKP (Nutanix Kubernetes Platform): nền tảng đa cluster, dựng trên Cluster API, chạy được trên AHV, vSphere, public cloud và bare metal, có thành phần quản lý tập trung và bộ addon quan sát, ingress, GitOps. NKP phát triển từ công nghệ của D2iQ mà Nutanix tiếp nhận.
  • Storage: Nutanix CSI cấp volume block (Volumes), file (Files, RWX) và object (Objects) từ chính cluster Nutanix.
  • Chém: hợp nếu doanh nghiệp đã chạy Nutanix HCI và muốn một đầu mối hỗ trợ cho compute, storage và Kubernetes. Không hợp nếu bạn cloud-native thuần, chỉ ở AWS, hoặc muốn tránh lock-in. Cộng đồng và tài liệu cộng đồng nhỏ hơn EKS hay Rancher, nên hỗ trợ từ hãng là phần bạn đang trả tiền.

Còn các tên khác

  • GKE, AKS: tương tự EKS trên Google Cloud và Azure. GKE có Autopilot (Google quản lý cả node).
  • OpenShift (Red Hat): distro doanh nghiệp đầy đủ, nhiều quy tắc riêng (SCC, Routes, Operators).
  • Cluster API (CAPI): không phải distro mà là cách khai báo vòng đời cluster bằng chính K8s. Nhiều nền tảng (kể cả NKP) dùng nó bên dưới.

Vì sao RKE2 + Rancher

  • On-prem trên hạ tầng sẵn có. Đội đã từng chạy Kubernetes on-prem nên mô hình vận hành quen thuộc.
  • Không tốn license để bắt đầu. RKE2 và Rancher là mã nguồn mở, chi phí duy nhất là VM.
  • Có đường nâng cấp có hỗ trợ. Rancher Prime (gói thương mại của SUSE) dùng cùng mã nguồn. Khi cần hỗ trợ 24x7, chuyển cluster hiện có sang Prime bằng cách đổi nguồn chart, không phải dựng lại.
  • An toàn và sẵn sàng cho mạng đóng. Profile CIS, hỗ trợ SELinux, cài từ package nội bộ và registry nội bộ.
  • Giữ nguyên cách triển khai hiện tại. Flux GitOps, Traefik ingress và Vault không phải đổi.

Các quyết định thiết kế chính

  • Hai cluster workload. Dev/stg dùng chung, production riêng. Mọi thay đổi, kể cả nâng cấp Kubernetes, áp dụng cho dev/stg trước.
  • Ba control-plane node mỗi cluster. etcd cần đa số để ghi, ba node chịu được mất một node.
  • Cilium làm lớp mạng, kèm network policy cho mọi namespace ứng dụng.
  • Traefik làm ingress, cài và quản lý phiên bản qua GitOps thay vì dùng bản đi kèm RKE2.
  • Flux GitOps cho mọi thứ sau khi cài cluster: add-on nền tảng và ứng dụng đều khai báo trong một repo GitOps.
  • cert-manager tự gia hạn chứng chỉ HTTPS bằng cách nối với CA của công ty (cần xác nhận CA hỗ trợ). Vault Secrets Operator chuyển secret từ Vault vào cluster.
  • Mỗi cluster một bản OpenSandbox (nếu có workload chạy code không tin cậy), vì custom resource của nó có phạm vi toàn cluster.
  • Giám sát bằng Prometheus, Grafana, Alertmanager trong mỗi cluster, xem được ngay trong console Rancher.

Add-on tùy chọn cho giai đoạn sau

Không nằm trong bản dựng ban đầu, thêm qua GitOps khi cần mà không đổi hạ tầng:

  • Kyverno: luật cluster viết bằng YAML (image chỉ từ registry nội bộ, bắt buộc runtime gVisor cho sandbox, default-deny NetworkPolicy cho namespace mới).
  • Hubble (một phần của Cilium): xem Pod nào nói chuyện với Pod nào và kết nối nào bị policy chặn. Bật trong cấu hình Cilium, không cài riêng.
  • VPA ở chế độ khuyến nghị (hoặc Goldilocks): đo CPU, RAM thật và gợi ý resource, không tự đổi Pod đang chạy.
  • Reloader: tự restart Pod khi Secret hoặc ConfigMap mà nó dùng thay đổi (ví dụ sau khi chứng chỉ được gia hạn).
  • OpenCost: báo cáo chi phí theo namespace hoặc ứng dụng. Chỉ đáng dùng nếu có chargeback, vì giá on-prem phải nhập tay.

Lộ trình thực hiện

  1. Chốt các quyết định mở (node access, CIDR, chứng chỉ, backup storage, storage CSI) trước khi cài.
  2. Hạ tầng: VM, IP, DNS, load balancer, firewall (trang tiếp theo).
  3. Chuẩn bị node: hệ điều hành và các thiết lập bắt buộc, bằng Ansible.
  4. Cài RKE2: server đầu tiên, join thêm server, rồi worker.
  5. Cài Rancher trên management cluster và đăng ký các cluster workload.
  6. Bootstrap Flux, rồi để Flux cài add-on: Traefik, cert-manager, Vault Secrets Operator, giám sát.
  7. Dựng guardrail: namespace, Pod Security, NetworkPolicy, quota.
  8. Bật backup etcd và thử khôi phục trên dev/stg.
  9. Di chuyển ứng dụng từng cái một, ứng dụng nền (database, operator) trước.

Storage và backup

  • Block storage: driver CSI cho hệ thống storage đã chọn, có storage class RWO hỗ trợ mở rộng volume, và một service account cho driver. Dung lượng ban đầu chủ yếu do Elasticsearch quyết định.
  • Shared storage (tùy chọn): storage class RWX cho phép chạy nhiều replica API cho ứng dụng chia sẻ file. Không có thì các thành phần đó chạy một replica.
  • Backup storage: object storage tương thích S3 nằm ngoài cả hai cluster, dùng cho snapshot etcd, snapshot Elasticsearch và backup volume. Cả ba công cụ ghi thẳng vào S3, và Velero chỉ hỗ trợ object storage.
  • Ưu tiên: object storage doanh nghiệp sẵn có do đội hạ tầng vận hành. Thay thế: một VM riêng chạy S3 tự host (ví dụ Garage), tách khỏi toolchain node để một sự cố không xóa cùng lúc cấu hình lẫn bản backup của nó.
  • Mỗi cluster và mỗi mục đích một bucket với một credential riêng. Cluster dev/stg không được ghi vào bucket production. Với production nên có bản sao thứ hai ở địa điểm khác.

Lệnh tham khảo

# 1. Tắt swap
swapoff -a
sed -i '/ swap / s/^/#/' /etc/fstab

# 2. Tắt firewalld
systemctl disable --now firewalld

# 3. NetworkManager bỏ qua interface của Cilium
cat > /etc/NetworkManager/conf.d/cilium.conf <<'EOF'
[keyfile]
unmanaged-devices=interface-name:cilium_*;interface-name:lxc*
EOF
systemctl reload NetworkManager

# 4. SELinux enforcing
getenforce                      # phải là Enforcing
dnf install -y container-selinux

# 5. Đồng bộ giờ
dnf install -y chrony
sed -i 's/^pool .*/server ntp.example.com iburst/' /etc/chrony.conf
systemctl enable --now chronyd

# 6. Yêu cầu của profile CIS (đường dẫn file sysctl có thể là /usr/share/rke2 hoặc /usr/local/share/rke2)
useradd -r -c "etcd user" -s /sbin/nologin -M etcd -U
cp -f /usr/share/rke2/rke2-cis-sysctl.conf /etc/sysctl.d/60-rke2-cis.conf

# 7. Tham số kernel cho Elasticsearch
echo 'vm.max_map_count=1048576' > /etc/sysctl.d/90-elasticsearch.conf
sysctl --system

rke2-selinux được cài kèm RKE2 từ repo hoặc gói offline, xem trang cài RKE2.

Dùng Ansible, đừng làm tay

Các thiết lập này không phải việc làm một lần: mỗi thành phần nền tảng sẽ thêm yêu cầu riêng (vm.max_map_count cho Elasticsearch, thiết lập mạng cho Cilium, runtime gVisor trên node sandbox), và mỗi lần thêm hoặc dựng lại node đều cần lại. Hãy để Ansible playbook trong Git làm việc đó: mọi thay đổi được review, lặp lại được và đội hạ tầng nhìn thấy.

# roles/k8s_node/tasks/main.yml (rút gọn)
- name: Disable swap
  ansible.posix.mount: {name: none, fstype: swap, state: absent}
- ansible.builtin.command: swapoff -a
- name: Stop and disable firewalld
  ansible.builtin.systemd: {name: firewalld, state: stopped, enabled: false}
- name: NetworkManager ignores Cilium interfaces
  ansible.builtin.copy:
    dest: /etc/NetworkManager/conf.d/cilium.conf
    content: |
      [keyfile]
      unmanaged-devices=interface-name:cilium_*;interface-name:lxc*
  notify: reload NetworkManager
- name: etcd user (CIS)
  ansible.builtin.user: {name: etcd, system: true, shell: /sbin/nologin, create_home: false}
- name: Kernel parameters
  ansible.posix.sysctl: {name: vm.max_map_count, value: "1048576", sysctl_file: /etc/sysctl.d/90-elasticsearch.conf, reload: true}

Phân chia trách nhiệm

  • Khuyến nghị: đội hạ tầng sở hữu OS nền (cấp phát, patch, hardening), đội nền tảng K8s sở hữu các thiết lập riêng cho Kubernetes và áp bằng Ansible.
  • Đề nghị đội hạ tầng giao VM cơ bản (OS, mạng, đăng ký, NTP) và cấp cho đội nền tảng quyền SSH có sudo trên mọi node. Nếu không được, đội hạ tầng chạy cùng playbook theo yêu cầu và phối hợp từng thay đổi.
  • Rủi ro: nếu công ty ép một baseline hardening cho mọi VM, node Kubernetes cần ngoại lệ cho các thiết lập ở trên. Nếu không baseline có thể bật lại firewalld hoặc swap và làm hỏng cluster.

Patch hệ điều hành

Patch OS nằm ngoài phạm vi cài đặt, nên thống nhất nguồn cập nhật và cửa sổ patch với đội hạ tầng trước khi lên production. Patch từng node một: di tản workload, patch, khởi động lại, trả node về phục vụ.

kubectl cordon NODE
kubectl drain NODE --ignore-daemonsets --delete-emptydir-data
# patch và reboot node
kubectl uncordon NODE

Với node có Pod dùng PodDisruptionBudget hoặc Elasticsearch, kiểm tra cluster đã green lại trước khi sang node kế tiếp.

Cài RKE2: cluster HA với 3 control plane

RKE2 là distro Kubernetes của SUSE Rancher, tập trung vào bảo mật và mạng đóng. Control plane chạy dạng static pod, runtime là containerd, và có thể bật sẵn profile CIS.

Trình tự

  1. Chuẩn bị node (trang trước) và load balancer cho cổng 6443 và 9345 trỏ vào 3 control plane.
  2. Cài và khởi động server đầu tiên (khởi tạo cluster và etcd).
  3. Cài và khởi động hai server còn lại, trỏ về VIP của load balancer (cổng 9345).
  4. Cài agent (worker) và join qua cùng VIP.
  5. Gắn label, taint cho node đặc biệt (ingress, sandbox).

Profile CIS

  • profile: cis bật hardening theo CIS Benchmark: kiểm tra quyền file, bắt buộc user etcd, sysctl, Pod Security Admission mặc định ở mức restricted (có namespace ngoại lệ), và một số NetworkPolicy mặc định cho các namespace hệ thống.

Cài Rancher và đăng ký các cluster

Rancher là management plane: một ứng dụng chạy trên cluster riêng (management cluster) để quản lý các cluster workload. Nó không phải nơi chạy ứng dụng của bạn.

Vai trò và nguyên tắc

  • Management cluster gồm 3 node RKE2, chỉ chạy Rancher và thành phần phụ trợ.
  • Rancher cho một console cho mọi cluster: sức khỏe, workload, log, phân quyền, nâng cấp Kubernetes.
  • Rancher ngừng thì ứng dụng vẫn chạy. Cluster workload hoạt động độc lập, chỉ mất khả năng quản lý qua console cho đến khi Rancher trở lại.
  • Cài Rancher trên một cluster RKE2 (hoặc k3s) bằng Helm. Rancher server cần HA, backup và nâng cấp đúng ma trận tương thích.

  • Khi cần hỗ trợ 24x7, chuyển sang Rancher Prime bằng cách đổi nguồn chart (cùng mã nguồn), không phải dựng lại cluster.

Bootstrap GitOps bằng Flux sau khi có cluster

Sau khi cài cluster, mọi thứ còn lại (add-on nền tảng và ứng dụng) được khai báo trong Git và Flux áp dụng. Không có gì được áp tay bằng kubectl.

Bootstrap trong mạng đóng

Cluster không ra internet, nên image của Flux, chart và Git đều lấy từ hệ thống nội bộ:

Nguyên tắc vận hành

Công việc định kỳ

  • Snapshot etcd mỗi 6 giờ, sao chép sang backup storage. Diễn tập khôi phục mỗi quý trên dev/stg: backup chưa từng restore thì chưa phải là backup.
  • Patch Kubernetes mỗi 1 đến 2 tháng. Nâng minor khoảng hai lần mỗi năm, luôn dev/stg trước.
  • Patch OS hàng tháng, từng node một, sau khi thống nhất nguồn cập nhật và cửa sổ patch (đề xuất, ngoài phạm vi dựng cluster).
  • Theo dõi hạn chứng chỉ (kể cả của chính cluster và Rancher), dung lượng volume, và cảnh báo Alertmanager.

Quyết định mở cần chốt trước khi cài

  • Quyền truy cập node: SSH sudo cho đội nền tảng, hay đội hạ tầng áp thay đổi.
  • Baseline hardening của công ty: nếu có, cần ngoại lệ cho các thiết lập node (firewalld, swap).
  • Chứng chỉ: CA công ty hỗ trợ phương thức cấp tự động nào (CA trung gian, Vault PKI, ACME).
  • Backup storage: object storage doanh nghiệp hay một VM riêng chạy S3 tự host.
  • Shared storage: có storage class RWX hay không.
  • Host vật lý: tối thiểu ba, với anti-affinity cho các vai trò đã nêu.
  • Dải IP nội bộ cluster: xác nhận 10.42.0.0/16 và 10.43.0.0/16 không trùng hệ thống nào node cần truy cập, hoặc chọn dải khác. Phải chốt trước khi cài.
  • Block storage: hệ thống storage và driver CSI do khách hàng chọn, cần storage class RWO có mở rộng volume và tương thích với phiên bản Kubernetes đã chọn.
  • Hệ điều hành: RHEL 9 (có hỗ trợ và cập nhật qua kênh Red Hat) hay Rocky Linux 9 (cùng mã nguồn, miễn phí, nhưng hỗ trợ cộng đồng và cần nguồn cập nhật riêng). RKE2 hỗ trợ cả hai và cách cài giống nhau.
  • Hỗ trợ vendor: khi nào chuyển sang Rancher Prime.

Checklist trước go-live

  1. Cả ba control plane, worker và sandbox nằm trên host vật lý khác nhau như thiết kế.
  2. Load balancer health check đúng, kể cả khi tắt thử một control plane.
  3. Snapshot etcd chạy tự động và đã khôi phục thành công trên dev/stg.
  4. Giám sát và cảnh báo hoạt động, có người nhận cảnh báo.
  5. Network policy mặc định chặn đã bật cho namespace ứng dụng.
  6. Credential khởi tạo (token RKE2, mật khẩu Rancher, key của dịch vụ) đã đổi và cất trong Vault.
  7. Quy trình nâng cấp đã chạy thử một vòng trên dev/stg.

Traefik: ingress cho cluster on-prem

Traefik là ingress controller và reverse proxy. Trong thiết kế này nó nhận traffic TCP từ load balancer layer-4, kết thúc TLS và định tuyến tới Service.

Vì sao tự cài qua GitOps

  • RKE2 có sẵn một ingress controller đi kèm, nhưng bản đó gắn với phiên bản RKE2. Cài Traefik bằng HelmRelease giúp bạn kiểm soát phiên bản và cấu hình trong Git, không bị đổi theo mỗi lần nâng cấp RKE2.
  • Vì vậy tắt ingress mặc định trong RKE2 (disable: rke2-ingress-nginx) và cài Traefik riêng.

Mô hình triển khai

  • Traefik chạy trên 2 ingress worker cố định (nodeSelector hoặc affinity theo label), mỗi node một Pod (DaemonSet hoặc Deployment với anti-affinity).
  • Service kiểu NodePort: 30080 (HTTP) và 30443 (HTTPS). Load balancer ngoài chuyển 80/443 tới các cổng này.
  • TLS kết thúc tại Traefik, chứng chỉ do cert-manager cấp.
  • Dùng PROXY protocol giữa load balancer và Traefik để thấy IP thật của client, và chỉ tin header PROXY từ địa chỉ load balancer.

IngressRoute và Middleware

Ngoài Ingress chuẩn, Traefik có CRD riêng mạnh hơn: IngressRoute và Middleware. Ví dụ đường nhận log có kiểm tra khóa nguồn, xóa header nhạy cảm và giới hạn tốc độ:

apiVersion: traefik.io/v1alpha1
kind: Middleware
metadata: {name: auth-check, namespace: logging}
spec:
  forwardAuth:
    address: http://auth-service.logging.svc:8080/verify
    authRequestHeaders: ["Authorization", "X-Source-Key"]
---
apiVersion: traefik.io/v1alpha1
kind: Middleware
metadata: {name: strip-auth, namespace: logging}
spec:
  headers:
    customRequestHeaders:
      Authorization: ""            # đặt rỗng để xoá header trước khi tới backend
---
apiVersion: traefik.io/v1alpha1
kind: Middleware
metadata: {name: rate-limit, namespace: logging}
spec:
  rateLimit:
    average: 100
    burst: 200
---
apiVersion: traefik.io/v1alpha1
kind: IngressRoute
metadata: {name: collector, namespace: logging}
spec:
  entryPoints: [websecure]
  routes:
    - match: Host(`logs.example.com`) && PathPrefix(`/v1/logs`)
      kind: Rule
      middlewares:
        - name: auth-check
        - name: strip-auth
        - name: rate-limit
      services:
        - name: collector
          port: 4318
  tls:
    secretName: logs-example-com-tls
  • Middleware chạy theo thứ tự khai báo. Ở ví dụ: kiểm tra khóa, rồi xóa header Authorization, rồi giới hạn tốc độ.
  • forwardAuth gọi một dịch vụ xác thực với header của request và cho qua nếu trả 2xx. Dịch vụ này thường tra Redis rồi tới database khi cache miss.
  • Các middleware hay dùng khác: ipAllowList (giới hạn IP, ví dụ cho cổng truy cập tạm của developer), redirectScheme, stripPrefix, compress, retry.
  • Traefik giữ kết nối TLS ngoài, còn Traefik tới Pod trong cluster là HTTP thường (hoặc HTTPS nếu cần mTLS nội bộ).

Lưu ý vận hành

  • Bật access log và metric Prometheus của Traefik, theo dõi tỷ lệ 4xx/5xx.
  • Trỏ DNS wildcard (ví dụ *.dev.example.com) về VIP ứng dụng để không phải đổi DNS mỗi khi thêm host.
  • Nếu mạng không cho phép PROXY protocol trên load balancer, dùng X-Forwarded-For và cấu hình forwardedHeaders.trustedIPs thay thế, nhưng chỉ tin header từ load balancer.
  • Tách địa chỉ Rancher và địa chỉ ứng dụng: Rancher có VIP riêng, không đi chung Traefik của cluster workload.

cert-manager, Vault Secrets Operator và Reloader

Ba công cụ giải quyết vòng đời của chứng chỉ và secret: cấp và gia hạn chứng chỉ tự động, đưa secret từ Vault vào cluster, và restart Pod khi chúng thay đổi.

cert-manager

Controller tự cấp và gia hạn chứng chỉ X.509 dưới dạng Secret. Hai khái niệm chính:

  • Issuer / ClusterIssuer: nguồn cấp chứng chỉ (CA nội bộ, Vault PKI, ACME, self-signed).
  • Certificate: khai báo chứng chỉ cần có (tên miền, thời hạn, Secret đích). cert-manager tạo và gia hạn trước khi hết hạn.
Nguồn cấpDùng khi
caCó sẵn một CA trung gian (cặp key và chứng chỉ trong Secret).
vault (PKI)Dùng Vault PKI engine làm CA công ty.
acmeCA nội bộ hoặc công cộng nói ACME (trong mạng đóng cần ACME server nội bộ).
Thủ côngCA không tự động hóa được: cấp chứng chỉ wildcard bằng tay, gia hạn mỗi năm và giám sát hạn.
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata: {name: company-ca}
spec:
  ca:
    secretName: company-intermediate-ca     # key và chứng chỉ của CA trung gian
---
apiVersion: cert-manager.io/v1
kind: Certificate
metadata: {name: apps-wildcard, namespace: traefik}
spec:
  secretName: apps-wildcard-tls
  duration: 2160h          # 90 ngày
  renewBefore: 360h        # gia hạn trước 15 ngày
  dnsNames:
    - "*.dev.example.com"
  issuerRef: {name: company-ca, kind: ClusterIssuer}
  • cert-manager cũng cấp chứng chỉ cho admission webhook của các operator (OpenTelemetry Operator, Kyverno…).
  • Thêm CA công ty vào trust của node và Pod (qua trust-manager hoặc volume) để chúng tin các dịch vụ nội bộ.
  • Theo dõi metric hạn chứng chỉ của cert-manager trong Prometheus và đặt cảnh báo.

Vault Secrets Operator (VSO)

Operator của HashiCorp đồng bộ secret từ Vault thành Secret Kubernetes, không cần sidecar hay sửa ứng dụng. Secret được giữ trong Vault, đưa vào cluster lúc chạy, không nằm trong Git hay image.

apiVersion: secrets.hashicorp.com/v1beta1
kind: VaultConnection
metadata: {name: vault, namespace: opensandbox}
spec:
  address: https://vault.example.com:8200
  caCertSecretRef: company-ca
---
apiVersion: secrets.hashicorp.com/v1beta1
kind: VaultAuth
metadata: {name: k8s-auth, namespace: opensandbox}
spec:
  vaultConnectionRef: vault
  method: kubernetes
  mount: kubernetes-devstg            # auth method của Vault, mỗi cluster một mount
  kubernetes:
    role: opensandbox
    serviceAccount: default
---
apiVersion: secrets.hashicorp.com/v1beta1
kind: VaultStaticSecret
metadata: {name: server-api-key, namespace: opensandbox}
spec:
  vaultAuthRef: k8s-auth
  mount: secret
  type: kv-v2
  path: platform/opensandbox/api-key
  refreshAfter: 60s
  destination:
    name: server-api-key              # Secret Kubernetes được tạo ra
    create: true
  rolloutRestartTargets:
    - kind: Deployment
      name: opensandbox-server        # restart khi giá trị đổi
  • VaultStaticSecret: secret tĩnh (KV). VaultDynamicSecret: secret ngắn hạn do Vault sinh (database credentials). VaultPKISecret: chứng chỉ từ Vault PKI.
  • Cách xác thực: Vault Kubernetes auth (bằng ServiceAccount). Mỗi cluster nên có mount auth riêng để cluster dev không đọc được secret của production.
  • rolloutRestartTargets cho phép VSO tự khởi động lại workload khi secret đổi.
  • Thay thế: External Secrets Operator (nhiều backend), Secrets Store CSI Driver (mount thẳng vào Pod).

Reloader

Theo dõi ConfigMap và Secret, tự rolling restart workload dùng chúng khi nội dung thay đổi. Hữu ích sau khi chứng chỉ được gia hạn hoặc giá trị Vault đổi, vì biến môi trường và file đã mount trong container không tự cập nhật.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  annotations:
    reloader.stakater.com/auto: "true"       # theo dõi mọi ConfigMap/Secret mà Deployment này dùng
    # hoặc chỉ định cụ thể:
    # secret.reloader.stakater.com/reload: "server-api-key"
Mẹo

VSO có rolloutRestartTargets cho secret của nó, còn Reloader bao quát cả ConfigMap và Secret do công cụ khác tạo (ví dụ chứng chỉ của cert-manager). Chọn một cách thống nhất cho từng loại để tránh restart hai lần.

Giám sát (Prometheus, Grafana, Alertmanager) và các add-on tùy chọn

Mỗi cluster có bộ giám sát riêng. Các add-on như Kyverno, VPA/Goldilocks, OpenCost thêm sau qua GitOps khi nhu cầu xuất hiện.

Prometheus, Grafana, Alertmanager

  • Prometheus thu thập metric (kéo theo chu kỳ) và lưu dạng time series. Grafana vẽ dashboard. Alertmanager nhận cảnh báo từ Prometheus, nhóm, khử trùng lặp và gửi đi (email, chat, webhook).
  • Cài bằng chart kube-prometheus-stack (dựa trên Prometheus Operator) hoặc chart Monitoring của Rancher, có sẵn dashboard và rule cho Kubernetes.
  • Giám sát trong từng cluster và xem được ngay trong console Rancher.
# Theo dõi một ứng dụng: ServiceMonitor
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata: {name: web, namespace: demo}
spec:
  selector:
    matchLabels: {app: web}
  endpoints:
    - port: metrics
      interval: 30s
---
# Cảnh báo: PrometheusRule
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata: {name: web-alerts, namespace: demo}
spec:
  groups:
    - name: web
      rules:
        - alert: HighErrorRate
          expr: sum(rate(http_requests_total{app="web",code=~"5.."}[5m])) / sum(rate(http_requests_total{app="web"}[5m])) > 0.05
          for: 10m
          labels: {severity: page}
          annotations: {summary: "Tỷ lệ lỗi 5xx trên 5% trong 10 phút"}

Những gì nên giám sát từ đầu

  • Sức khỏe control plane: độ trễ API server, etcd (fsync, leader, dung lượng DB).
  • Node: CPU, RAM, đĩa, trạng thái NotReady.
  • Pod: restart liên tục, Pending, OOMKilled.
  • Volume: dung lượng PVC còn lại. Chứng chỉ: số ngày còn lại (cert-manager).
  • Ingress: tỷ lệ lỗi và độ trễ ở Traefik. Backup: lần chạy gần nhất thành công của etcd snapshot, Velero.
  • Cấu hình lưu trữ metric: retention theo dung lượng volume, dùng storage class RWO. Cân nhắc remote write nếu cần lưu lâu.
  • Alertmanager route theo severity và team. Cảnh báo hạ tầng được chuyển cho đội hạ tầng.

Kyverno: policy engine

Viết luật cluster bằng YAML (validate, mutate, generate, verify image). Ví dụ các luật gợi ý cho nền tảng:

# Chỉ cho phép image từ registry nội bộ
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata: {name: allowed-registries}
spec:
  validationFailureAction: Enforce
  rules:
    - name: only-internal-registry
      match:
        any:
          - resources: {kinds: [Pod]}
      validate:
        message: "Image phải đến từ registry.example.com"
        pattern:
          spec:
            containers:
              - image: "registry.example.com/*"
---
# Tự tạo NetworkPolicy default-deny cho namespace mới
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata: {name: default-deny}
spec:
  rules:
    - name: generate-default-deny
      match:
        any:
          - resources: {kinds: [Namespace]}
      generate:
        apiVersion: networking.k8s.io/v1
        kind: NetworkPolicy
        name: default-deny
        namespace: "{{request.object.metadata.name}}"
        synchronize: true
        data:
          spec:
            podSelector: {}
            policyTypes: [Ingress, Egress]

Luật khác thường gặp: bắt buộc runtimeClassName: gvisor cho Pod ở namespace sandbox, bắt buộc label, cấm tag latest. Chi tiết về policy engine có ở trang PSA và policy.

Hubble

Lớp quan sát luồng mạng của Cilium. Bật trong cấu hình Cilium của RKE2 (xem trang cài RKE2), không phải cài riêng. Rất hữu ích khi network policy trở nên chặt: hubble observe --verdict DROPPED cho thấy kết nối nào bị chặn và vì sao. Xem trang CNI để biết lệnh.

OpenCost

Báo cáo chi phí theo namespace, workload, label. Với on-prem, giá không có sẵn nên phải nhập tay giá CPU, RAM, lưu trữ. Chỉ đáng triển khai nếu có chargeback hoặc showback cho các đội.

Velero

Backup và khôi phục tài nguyên Kubernetes cùng dữ liệu volume. Hai cách sao lưu volume:

  • CSI snapshot: dùng VolumeSnapshot của driver CSI (nhanh, cần driver hỗ trợ).
  • File-system backup (node-agent, dùng Kopia): sao chép file trong volume, dùng được với mọi loại volume nhưng chậm hơn và Pod đang ghi thì cần cẩn thận.
velero install \
  --provider aws \
  --plugins velero/velero-plugin-for-aws:v1.11.0 \
  --bucket devstg-velero \
  --secret-file ./velero-credentials \
  --backup-location-config region=us-east-1,s3ForcePathStyle=true,s3Url=https://s3.example.com \
  --use-node-agent

# Lịch backup hàng ngày, giữ 30 ngày
velero schedule create daily-apps \
  --schedule="0 2 * * *" \
  --include-namespaces app-studio \
  --default-volumes-to-fs-backup \
  --ttl 720h

velero backup get
velero restore create --from-backup daily-apps-20261030020000

Số phiên bản plugin ở trên chỉ là ví dụ, chọn bản tương thích với phiên bản Velero bạn cài.

  • Khôi phục sang namespace khác bằng --namespace-mappings, hữu ích để thử restore mà không đè dữ liệu thật.
  • Backup của volume dùng chung (ví dụ file build của ứng dụng) là nguồn sự thật duy nhất nên cần lịch backup riêng.

Cẩn thận

Backup chưa từng khôi phục thử thì chưa đáng tin. Đặt lịch diễn tập định kỳ (etcd mỗi quý, dữ liệu ứng dụng khi thay đổi lớn), ghi thời gian khôi phục thực tế (RTO) và lượng dữ liệu có thể mất (RPO) để so với yêu cầu.

Vì sao dùng ECK

  • Operator tự lo những phần dễ sai: cấp và gia hạn chứng chỉ TLS, nâng cấp phiên bản từng node không mất dữ liệu, drain node trước khi tắt, giữ đúng thành viên cluster khi Pod đến và đi.
  • Đây là cách duy nhất Elastic hỗ trợ: Helm chart của Elastic đã được archive từ 5/2023.
  • Tính năng cần dùng nằm trong license Basic (miễn phí). Basic không có hỗ trợ vendor và các tính năng doanh nghiệp như searchable snapshots, autoscaling. Thiết kế không phụ thuộc vào chúng.
  • Tự viết và duy trì cấu hình riêng thì phải làm lại gia hạn chứng chỉ và nâng cấp an toàn, tốn công và có rủi ro mất dữ liệu.

  • Số node lẻ để luôn có đa số khi bầu leader: 3 node chịu mất 1, 5 node chịu mất 2.
  • RAM đặt gấp đôi heap, phần còn lại dành cho file cache mà Elasticsearch dựa vào để tìm kiếm nhanh.

  • Mỗi Pod có volume riêng (RWO) từ block storage, không dùng chung. Elasticsearch đã giữ bản sao shard trên node khác, storage dùng chung chỉ thêm chi phí và điểm lỗi chung.

Vòng đời dữ liệu

Mỗi workspace ghi vào một data stream: một đích ghi có tên, phía sau là chuỗi index do Elasticsearch tự quản lý. Hai cơ chế phối hợp:

  • Rollover: đóng index hiện tại và mở index mới khi đạt giới hạn kích thước hoặc tuổi, giữ mỗi index ở cỡ dễ quản lý.
  • Lifecycle policy (ILM): xóa index khi quá thời gian lưu của workspace.
PUT _ilm/policy/logs-30d
{
  "policy": {
    "phases": {
      "hot": {"actions": {"rollover": {"max_primary_shard_size": "50gb", "max_age": "1d"}}},
      "delete": {"min_age": "30d", "actions": {"delete": {}}}
    }
  }
}
Thời gian lưu đo từ rollover, không phải từ lúc tạo index

Bộ đếm xóa bắt đầu khi index rollover. Thời gian lưu thực tế bằng khoảng rollover cộng với thời gian lưu cấu hình. Nên nói rõ với khách hàng để cam kết “lưu 30 ngày” không bị hiểu thành con số chính xác tuyệt đối.

  • Các mức lưu cho workspace: 7, 30, 60, 90, 180, 365 ngày (mặc định 30). Có thể cho workspace chọn thời gian tùy chỉnh.
  • Policy chuẩn nằm trong Git và được áp bằng một Job do GitOps quản lý gọi API Elasticsearch, nên mọi thay đổi có version và dấu vết. Policy tùy chỉnh do ứng dụng tạo khi tạo workspace và tạo lại mỗi ngày nếu thiếu, dựa trên database của ứng dụng.
  • Quản lý policy bằng StackConfigPolicy của operator cần license Enterprise nên không dùng.

Backup bằng snapshot

Snapshot ghi ra repository ngoài cluster theo lịch và là tăng dần: sau lần đầu chỉ chép phần thay đổi. Elasticsearch 8 trở lên ghi vào S3 không cần plugin.

PUT _snapshot/s3-backup
{"type": "s3", "settings": {"bucket": "devstg-es-backup", "endpoint": "https://s3.example.com", "path_style_access": true}}

PUT _slm/policy/daily
{
  "schedule": "0 30 1 * * ?",
  "name": "<daily-{now/d}>",
  "repository": "s3-backup",
  "config": {"indices": "*"},
  "retention": {"expire_after": "30d", "min_count": 5, "max_count": 50}
}

Khóa truy cập S3 đưa vào keystore của Elasticsearch qua spec.secureSettings của resource ECK. Lịch snapshot và thời gian giữ snapshot do SLM policy quy định, giữ trong Git và áp bằng cùng Job.

Yêu cầu nền tảng

  • Đủ worker trên các host vật lý khác nhau. Block storage khoảng 1 TiB mỗi node production, 200 GiB cho staging.
  • Backup storage S3. Kernel parameter vm.max_map_count trên worker.

OpenTelemetry Collector và Operator

Collector nhận, xử lý và chuyển tiếp dữ liệu quan sát (log, metric, trace). Trong ví dụ này nó nhận lô log từ shipper (như Fluent Bit) và ghi sang Elasticsearch.

Hiện trạng và vấn đề

  • Một instance Collector Contrib chạy trong Docker Compose: không dự phòng, một điểm lỗi duy nhất.
  • Hàng đợi gửi chỉ nằm trong bộ nhớ: lô log đang chờ sẽ mất khi container restart.
  • Mở rộng thủ công, không hấp thụ được đỉnh tải.

Phù hợp cho proof of concept nhưng không có khả năng chịu lỗi: một lần restart có thể làm rơi lặng lẽ các lô log đang gửi.

Cách tiếp cận

  • Dùng OpenTelemetry Operator (cùng mô hình với ECK): khai báo resource OpenTelemetryCollector với phiên bản, số replica và cấu hình, operator sinh và giữ đồng bộ StatefulSet và Service.
  • Chạy dạng StatefulSet, không phải Deployment: mỗi Pod có volume riêng chứa hàng đợi gửi trên đĩa. Pod restart thì gắn lại volume của mình và gửi tiếp các lô còn trong hàng đợi.
  • Không autoscale (không dùng HPA): nếu Pod bị scale-down tự động thì không bảo đảm hàng đợi trên đĩa của Pod bị xóa đã gửi xong. Số replica cố định theo tải dự kiến.
  • Chứng chỉ cho admission webhook của operator do cert-manager cấp.

Kích thước (nháp)

Môi trườngReplicaRAM/PodĐĩa hàng đợi/Pod
Development1-2512 MiB2 GiB
Staging, production31 GiB10 GiB (xác nhận theo tải thật)

Luồng yêu cầu

  1. Log shipper gửi log qua HTTPS tới một IngressRoute của Traefik.
  2. Traefik áp ba middleware theo thứ tự: forwardAuth kiểm tra khóa nguồn, bước kế xóa header Authorization, và rateLimit tùy chọn giới hạn tốc độ.
  3. Để kiểm tra khóa, forwardAuth tra Redis và nếu miss thì tra PostgreSQL (không có dịch vụ xác thực riêng).
  4. Traffic được chấp nhận tới Service của Collector, phân tán sang các Pod, mỗi Pod có volume riêng.
  5. Mỗi Pod ghi sang Elasticsearch qua HTTPS.

Client tới Traefik và Collector tới Elasticsearch dùng HTTPS, còn Traefik tới Collector là HTTP thường trong cluster. Khóa nguồn không bao giờ tới Collector vì Traefik đã xóa header.

Phần xác thực tới Elasticsearch (user, mật khẩu, CA) được lấy từ Secret và không ghi trong cấu hình. Dùng bản Contrib đầy đủ lúc đầu, về sau có thể build image Collector tối giản.

GitOps và thứ tự

  • Operator cài trước, resource OpenTelemetryCollector chỉ áp sau khi operator báo Ready (dùng dependsOn của Flux).
  • Thay đổi cấu hình là một commit, operator tự tạo lại Pod theo thứ tự.

Vòng đời dữ liệu và backup

  • Component này không giữ dữ liệu dài hạn. Mỗi lô log chỉ nằm ngắn trong hàng đợi giữa lúc xử lý và lúc ghi thành công vào Elasticsearch. Nếu Elasticsearch tạm không sẵn sàng, hàng đợi giữ lô trên đĩa và thử lại. Không có thời gian lưu cần cấu hình.
  • Volume hàng đợi không cần backup snapshot: nó là bộ đệm tạm. Mất nó chỉ mất tối đa vài phút đến vài giờ lô log đang bay, không mất khả năng tìm log lịch sử (nằm trong Elasticsearch và được backup riêng).

Quyết định còn mở

  • Số replica cố định cho staging và production (3 hay nhiều hơn, tùy lưu lượng thật).
  • Dung lượng volume hàng đợi.
  • Có build image Collector tối giản sau này hay không.
  • Anti-affinity ở mức bắt buộc (required) hay ưu tiên (preferred).

OpenSandbox và gVisor: chạy code không tin cậy

OpenSandbox là dịch vụ mã nguồn mở (Apache-2.0) tạo môi trường cô lập, sống ngắn theo yêu cầu và chèn một daemon thực thi lệnh nhỏ (execd) vào từng môi trường. Mọi thứ chạy trong sandbox phải coi là code không tin cậy, ví dụ code do LLM sinh ra hay test trình duyệt tự động.

Vấn đề với mô hình Docker

Khía cạnhHiện tạiHệ quả
HostingMột VM, Docker ComposeĐiểm lỗi duy nhất, không rolling update.
Cô lậpContainer Docker thường, server mount Docker socketTài liệu của dự án gọi việc mount socket là “tương đương root trên host Docker”.
Đặc quyềnLệnh trong sandbox chạy với quyền rootThoát khỏi sandbox nghĩa là chiếm host.
Truy cậpMỗi sandbox một cổng host độngMô hình “một cổng một sandbox” không áp dụng được trên Kubernetes.

Cách tiếp cận trên Kubernetes

  • Dùng Kubernetes runtime có sẵn và operator của nó. Server tạo resource BatchSandbox thay vì gọi Docker. Controller (cài từ Helm chart của dự án) biến mỗi resource thành một Pod và xóa Pod khi sandbox được trả hoặc hết hạn. Docker socket biến mất, không thành phần nào cần root trên node.
  • Cô lập bằng node riêng và gVisor. Pod sandbox chạy trên node chuyên dụng có taint, dưới gVisor: kernel chạy ở user space, chặn system call của sandbox, nên root trong sandbox không bao giờ chạm kernel của host. Node sandbox: 1 ở dev/stg, 2 ở production. Server và controller chạy trên worker thường. Ngoài sandbox, chỉ thành phần hệ thống ở cấp node (như agent Cilium) chạy trên node sandbox.
  • Chỉ truy cập trong cluster. Server chỉ tới được từ trong cluster. Client gọi execd trực tiếp trên địa chỉ Pod sandbox. Không có điểm vào công khai. Có thể tạm mở một hostname cho developer (giới hạn IP bằng Traefik) khi test và xóa lúc go-live.
  • Mỗi mức tin cậy một namespace. opensandbox-system (controller, đặc quyền nhất), opensandbox (server mà client nói chuyện), opensandbox-workloads (Pod sandbox, nơi chạy code không tin cậy). Mỗi namespace có policy bảo mật riêng.
  • Một bản cài mỗi cluster vì custom resource và controller có phạm vi toàn cluster. Ở dev/stg, development và staging dùng chung, client tách bằng namespace, quota và network policy.
  • Giao qua GitOps, trừ phần cài gVisor ở cấp node. Chart và image mirror nội bộ và ghim theo digest.

Cài gVisor trên node sandbox

# Ansible hoặc tay, chỉ trên node sandbox: cài runsc và shim cho containerd,
# rồi khai báo runtime handler "runsc" cho containerd (cách cài thay đổi theo phiên bản gVisor).

kubectl label node sbx-1 sandbox=true
kubectl taint node sbx-1 sandbox=true:NoSchedule
apiVersion: node.k8s.io/v1
kind: RuntimeClass
metadata: {name: gvisor}
handler: runsc
scheduling:
  nodeSelector: {sandbox: "true"}
  tolerations:
    - {key: sandbox, operator: Equal, value: "true", effect: NoSchedule}

Pod muốn chạy sandbox chỉ cần runtimeClassName: gvisor: RuntimeClass tự đặt Pod lên node sandbox và gắn toleration. Tham số của gVisor cần chỉnh, gồm một thiết lập Cilium cho phép Pod gVisor truy cập Service trong cluster, được áp lúc dựng cluster. Cách cài gVisor có thể đổi theo thời gian, theo dõi tài liệu chính thức.

Rủi ro được chấp nhận: quyền của controller

Role của controller trong chart của dự án có thể tạo Pod ở namespace bất kỳ và đọc secret toàn cluster, và chart không cho thu hẹp. Giảm thiểu bằng admission policy giới hạn namespace, mức PSA restricted, network policy chỉ cho controller gọi Kubernetes API, và image ghim digest.

Luồng một yêu cầu

  1. Yêu cầu sandbox: ứng dụng xin server một sandbox, xác thực bằng API key. Network policy chỉ cho client được duyệt tới server.
  2. Server tạo BatchSandbox: API server kiểm tra quyền của server (RBAC, chỉ trong namespace workloads), admission policy (đúng namespace, yêu cầu gVisor, không phải snapshot) và quota.
  3. Controller tạo Pod sandbox: bộ kiểm tra thứ hai: LimitRange, PSA baseline, admission policy từ chối Pod thiếu gVisor hoặc có API token, và quota. RuntimeClass đặt Pod lên node sandbox.
  4. Chạy lệnh: client gửi lệnh thẳng tới execd trên địa chỉ Pod, xác thực bằng token execd. Từ bên trong, sandbox chỉ tới được DNS và registry npm nội bộ; mạng nội bộ, internet và Kubernetes API đều bị chặn.

Server không chuyển tiếp traffic lệnh, chỉ quản lý vòng đời sandbox. Restart server không ảnh hưởng sandbox đang chạy vì trạng thái nằm trong resource BatchSandbox.

Dữ liệu, backup và yêu cầu nền tảng

  • OpenSandbox không giữ dữ liệu dài hạn. Trạng thái mỗi sandbox nằm trong resource BatchSandbox do Kubernetes lưu.
